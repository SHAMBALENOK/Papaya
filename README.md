## Коротко о сервисе

Papaya — веб-сервис, который отвечает на один вопрос: **какие олимпиады дают БВИ в нужном мне университете?**

Сервис собирает официальные перечни олимпиад РСОШ и связывает их с университетами. Школьнику не нужно перебирать сайты вузов и приказы: он находит свой университет в каталоге, видит список олимпиад, дающих поступление без вступительных испытаний, открывает олимпиаду и переходит на её официальный сайт.

Продуктовая идея целиком описывается одной цепочкой:

```text
Университет → олимпиады, дающие БВИ → информация об олимпиаде → официальный сайт
```

Всё, что не поддерживает эту цепочку, в Papaya сознательно не делается: ни календаря олимпиад, ни расписания этапов, ни дедлайнов, ни организаторов, ни рекомендательных алгоритмов. Это агрегатор и каталог — не система поступления.

## Как это работает

| Роль | Что делает |
|------|-----------|
| **Школьник** (гость или зарегистрированный) | Ищет университет или олимпиаду, смотрит каталоги и страницы сущностей. Регистрация для этого не нужна. |
| **Представитель университета** | Управляет связями **своего** университета с олимпиадами: выбирает существующие олимпиады из каталога и заявляет, что вуз даёт за них БВИ. Новые олимпиады не создаёт. |
| **Администратор Papaya** | Ведёт каталог олимпиад и университетов, загружает документы РСОШ и подтверждает импорт, модерирует заявки БВИ, управляет пользователями и ролями. |

Пользовательский сценарий целиком:

```text
Открыть Papaya
      ↓
Найти университет
      ↓
Открыть университет
      ↓
Увидеть олимпиады, дающие БВИ
      ↓
Открыть олимпиаду
      ↓
Увидеть основную информацию и перейти на официальный сайт
```

Дополнительно на странице олимпиады доступен обратный путь — список университетов, которые дают БВИ за неё.

## Модель данных

```text
University ──(university_olympiads)── Olympiad ──(source_doc_id)── Docs
        │                                 │
        └──── PENDING / CONFIRMED ────────┘
```

| Таблица | Что хранит |
|---------|-----------|
| `users` | Профиль, роль (`USER` / `EDITOR` / `ADMIN`), привязка представителя к университету (`university_id`) и признак активности (`isActive`): заблокированный администратор не считается администратором. |
| `universities` | Университет: полное название, краткое название, описание, официальный сайт, две картинки (`preview_image` для карточек и `image` для страницы), нормализованное имя для защиты от дублей. |
| `olympiads` | Олимпиада: название, описание, официальный сайт, две картинки (`preview_image` для карточек и `image` для страницы), источник информации, статус актуальности (`PUBLISHED` / `ARCHIVED`), причина архива (`RSOSH_ABSENT` / `MANUAL`), документ-источник. |
| `university_olympiads` | Связь «университет даёт БВИ за олимпиаду» со статусом заявки (`PENDING` / `CONFIRMED`), автором заявки (`createdBy`) и администратором, подтвердившим связь (`confirmedBy`). Уникальность по паре гарантируется индексом в БД. |
| `docs` | Документ-источник: файл или ссылка, тип, контрольная сумма, состояние обработки и раздел `metadata['rsosh']` с состоянием прогона импорта, сводкой и кандидатами. |

Ключевые решения:

- **Олимпиада — единая каноническая сущность.** Записей «олимпиада 2026» и «олимпиада 2027» в каталоге нет: одна запись на олимпиаду независимо от года.
- **Университет не создаёт копию олимпиады.** Связь ссылается на существующую запись каталога; уникальный индекс по паре делает «две одинаковые связи» невозможными даже напрямую в базе.
- **Заявка ≠ публичный факт.** `PENDING`-связь видна представителю своего университета и администратору, в публичных списках — только `CONFIRMED`.
- **Архив, а не удаление.** Олимпиада, исчезнувшая из перечня РСОШ, переводится в `ARCHIVED`: запись сохраняется, а интерфейс показывает, что олимпиады больше нет в актуальном перечне.
- **Архивная олимпиада не принимает новых связей БВИ.** Заявка «университет даёт БВИ» означает «принимает поступление сейчас», а для олимпиады вне перечня это неверно: заявка получает 409. Уже подтверждённые связи при этом сохраняются и помечаются историческими (`is_historical`) — архив меняет актуальность, а не историю.
- **Не удалять, а архивировать.** У олимпиады есть история: подтверждённые связи, документ-источник, путь по перечню РСОШ. Физического удаления каталога в системе нет вообще — ни в слое данных, ни в API.
- **Причина архива — обязательна.** Статус один, а решение принимают два механизма, поэтому у архивной записи есть причина: `RSOSH_ABSENT` (нет в перечне РСОШ — вернёт импорт) или `MANUAL` (исключил администратор — вернуть можно вручную). Вернуть запись, исчезнувшую из перечня РСОШ, вручную нельзя: кнопка была бы без смысла, вернуть её должен перечень.
- **Снятый кандидат не «исчезает».** Если администратор снял строку в preview, она не считается отсутствующей в перечне: ошибка распознавания одной строки не архивирует существующую олимпиаду.
- **Картинок две.** `preview_image` показывается в карточках каталога, `image` — на странице сущности; если одно поле не заполнено, интерфейс берёт второе.
- **Документ — источник данных.** У олимпиады хранится `source_doc_id`, поэтому всегда видно, откуда взялась информация: страница олимпиады показывает источник через `GET /api/v1/olympiads/{id}/source` (публично и без доступа к самому файлу). Внутренний `source_doc_id` в публичных ответах не отдаётся; источник всегда отвечает `200` — у ручной записи он тоже есть, это «создано администратором Papaya».
- **Публичная модель минимальна.** Ответ олимпиады содержит только пользовательские поля (`id`, `name`, `description`, `official_url`, `preview_image`, `image`, `source_url`, `status`). Служебные `name_norm`, `source_doc_id`, `createdAt`, `updatedAt`, `archive_reason` наружу не выходят: они нужны импорту и панели администратора, а посетителю объяснения не дают.
- **Краткое название — главное.** В карточках, каталоге и заголовках страниц сначала идёт краткое название (`МФТИ`), полное — уточнением под ним. Полное название нигде не прячется.
- **Отдельной сущности «организация» нет.** Ни организаторы олимпиад, ни школы Papaya не моделирует: это лишний уровень абстракции для единственного типа участника.

## Роли и права

| Действие | Школьник / гость | Представитель университета | Администратор |
|----------|------------------|---------------------------|---------------|
| Каталоги, поиск, страницы университетов и олимпиад | ✅ | ✅ | ✅ |
| Связать свой университет с существующей олимпиадой | ❌ | ✅ (только свой вуз) | ✅ (любой вуз) |
| Подтвердить или снять связь БВИ | ❌ | ❌ | ✅ |
| Создать/изменить олимпиаду | ❌ | ❌ | ✅ |
| Создать/изменить университет | ❌ | ❌ | ✅ |
| Загрузить документ РСОШ и запустить импорт | ❌ | ❌ | ✅ |
| Управление пользователями и ролями | ❌ | ❌ | ✅ |
| Архивировать олимпиаду и возвращать её вручную | ❌ | ❌ | ✅ |

Правила проверяются в одном месте — `app/core/deps.py`; object-level проверка «свой ли университет» обязательна и на записи, и на чтении.

Инвариант роли: представитель — это «роль + привязка к университету», а не отдельный флаг. Поэтому `EDITOR` без `university_id` невозможен — это проверяет и приложение, и CHECK-ограничение в БД (`ck_users_representative_needs_university`, миграция `0006`). Роль и привязка меняются **одним** запросом `POST /api/v1/admin/role/{user_id}`: обычному пользователю нельзя привязать вуз «просто так», а администратору привязка не мешает и сохраняется, чтобы снятие администратора вернуло его в представители, а не в обычные пользователи. Отдельного маршрута «привязать университет» нет: два способа выдать права означали бы, что один из них обходит проверки.

Последнего активного администратора нельзя заблокировать или понизить (409): иначе зайти в панель будет некому. Со вторым администратором понижение допустимо.

Проверка атомарна: она выполняется под блокировкой строк администраторов (`SELECT ... FOR UPDATE` в порядке `id`) в той же транзакции, что и сама операция. Без этого две параллельные операции (понизить первого администратора и заблокировать второго) каждая увидела бы, что «второй остаётся», и вместе оставили бы систему без единого активного `ADMIN`.

Права на связи БВИ: представитель создаёт заявку по **актуальной** олимпиаде и может отозвать её, пока она `PENDING`; снять подтверждение может только администратор. Подтверждённая связь — публичный факт, поэтому её удаление решает администратор, а не автор заявки.

Модерация — три явных действия вместо «любой смены статуса»:

| Действие | Что делает |
|----------|-----------|
| `confirm` | `PENDING` → `CONFIRMED`: связь становится публичной |
| `reject`  | заявка отклонена, связь удаляется |
| `revoke`  | подтверждение отозвано, связь удаляется |

Перехода `CONFIRMED → PENDING` в модели нет: это не состояние заявки, а отзыв публичного факта. Такая запись не показывалась бы в каталоге и висела бы в очереди как будто университет подал заявку заново. Поле `confirmedBy` существует ровно у `CONFIRMED` и указывает на администратора, который подтвердил связь.

## Импорт документов РСОШ

Олимпиада попадает в каталог **двумя способами** и только двумя:

1. **Импорт официального документа РСОШ** — основной путь.
2. **Ручное создание администратором** — резервный путь.

Массовый импорт «произвольных таблиц» (бывший `POST /api/v1/events/add_events_via_tables`) в проекте отсутствует: ни маршрута, ни кода, ни кнопки в интерфейсе.

### Pipeline

```text
Document
    ↓ определение типа файла (сигнатура, не только расширение)
Предобработка растра + определение ориентации (0/90/180/270)
    ↓
Извлечение: нативное чтение XLSX → таблицы PDF с текстовым слоем → OCR скана/изображения
    ↓
Детекция и реконструкция таблиц (линии рамки, объединённые и многострочные ячейки)
    ↓
Нормализация ячеек (переносы строк, кавычки, «ё», зеркальная шапка РСОШ)
    ↓
Извлечение олимпиад (поиск колонки с названием, отбрасывание служебных строк)
    ↓
Валидация (длина названия, мусор, уверенность распознавания)
    ↓
Дедупликация: точное совпадение → merge, близкое → merge, сомнительное → на проверку
    ↓
Импорт preview (ничего не записано)
    ↓ подтверждение администратором
Создание/обновление олимпиад + архивирование исчезнувших из перечня
```

Особенности, которые учитывает импортёр:

- **XLSX** читается нативно (openpyxl): многострочные ячейки, объединённые по вертикали диапазоны, несколько листов;
- **PDF с текстовым слоем** разбирается по структуре документа (pdfplumber), OCR не применяется зря;
- **скан без текстового слоя** рендерится в растр (300 dpi) и распознаётся Tesseract (`rus+eng`) с передачей координат слов;
- **повёрнутые страницы** (90/180/270) определяются через OSD Tesseract, при отказе OSD — сравнительным распознаванием кандидатов;
- **«заваленные» страницы** выпрямляются по оценке наклона;
- **таблица на нескольких страницах** собирается в одну, повтор шапки отбрасывается, шапка первой страницы используется для всех следующих;
- **зеркально отрисованная шапка** (особенность части документов РСОШ) распознаётся и разворачивается;
- **служебные строки** (шапка письма, реквизиты приказа, подписи) в каталог не попадают;
- **пустой или нечитаемый документ** не импортируется молча: в статусе появляется `failed` с понятной причиной.

### API импорта

| Маршрут | Назначение |
|---------|-----------|
| `POST /api/v1/docs/upload` | загрузить документ-источник (`type=RSOSH_LIST`, `UNIVERSITY_ORDER`, `OTHER`) |
| `POST /api/v1/imports/rsosh` | запустить импорт документа |
| `GET /api/v1/imports` | список прогонов импорта |
| `GET /api/v1/imports/{id}` | состояние, сводка и предупреждения |
| `GET /api/v1/imports/{id}/preview` | кандидаты: что будет создано, что обновлено, что требует проверки |
| `POST /api/v1/imports/{id}/confirm` | применить импорт (`skip` — исключённые `name_norm`, `archive_missing`) |
| `POST /api/v1/imports/{id}/reject` | отклонить результаты, ничего не записав |

Состояние прогона хранится в `docs.metadata['rsosh']` (`processing` / `review` / `approved` / `rejected` / `failed`) — отдельная таблица прогонов не нужна, потому что прогон всегда относится к конкретному документу.

Запуск по умолчанию — фоновая задача Celery (`python -m app.rsosh.worker_run <doc_id>`), с автоматическим переходом на выполнение в процессе API, если брокер недоступен (`RSOSH_EXECUTION=auto|celery|inline`).

## Возможности

Реализовано:

- публичные каталоги университетов и олимпиад с поиском (регистр, переносы строк, частичные совпадения);
- единый поиск по обоим каталогам `GET /api/v1/search?q=…`;
- страницы университета и олимпиады, двусторонняя связь БВИ;
- заявки представителя университета и модерация заявок администратором;
- ручное создание и правка университетов и олимпиад администратором;
- архив олимпиад и автоматическое архивирование исчезнувших из перечня РСОШ;
- загрузка документов-источников и импорт РСОШ с preview и подтверждением;
- аутентификация (JWT в HttpOnly-cookies), профили, роли и object-level доступ;
- версионный кэш профилей в Redis; каталоги читаются напрямую из PostgreSQL, чтобы пользователь не видел устаревшую карточку после правки;
- health/readiness-маршруты и Docker healthcheck;
- миграции Alembic, применяемые автоматически при старте;
- автотесты: бизнес-логика, права, все форматы импорта (XLSX, PDF, скан, поворот, изображение), дедупликация и архивирование.

Не реализовано сознательно (следующие шаги, а не MVP): расписание и этапы олимпиад, дедлайны, результаты, сезоны/издания, другие льготы кроме БВИ, организаторы, школы, рекомендации, мобильное приложение, платежи.

## Архитектура

- **Frontend** — SPA на vanilla JS без сборщика (hash-роутер, дизайн-система в `app/frontend`), работает с API по `/api/v1` и JWT-cookies. Публичные страницы доступны гостю.
- **Backend** — FastAPI (async): роутеры `auth`, `user`, `universities`, `olympiads`, `docs`, `imports`, `search`, `admin`, `health`; правила доступа — в `app/core/deps.py`; слой доступа к данным — в `app/database`; Pydantic-схемы — в `app/schemas`.
- **Импорт РСОШ** — пакет `app/rsosh`: `filetypes` → `preprocessing` → `ocr` → `tables` → `normalization` → `parsing` → `validation` → `matching` → `states` → `persist` → `processor`.
- **PostgreSQL** — основная БД, схема управляется Alembic (`migrations/versions`).
- **Redis** — версионный кэш профилей, брокер и бэкенд Celery.
- **Celery** — очередь `heavy` для фонового импорта документов.
- **Tesseract OCR + OpenCV + pdfplumber + pypdfium2 + openpyxl** — распознавание и реконструкция таблиц документов РСОШ.
- **Docker Compose** — сервисы `postgres`, `redis`, `web`, `celery`, `pgadmin` и профиль `testing` для тестов.

## Стек технологий

- **Backend:** Python 3.11, FastAPI, Uvicorn, Gunicorn, Pydantic, PyJWT, bcrypt, Werkzeug.
- **База данных:** PostgreSQL 16, SQLAlchemy 2 (async), asyncpg, Alembic.
- **Импорт РСОШ:** pdfplumber, pypdfium2, pytesseract (Tesseract `rus`/`eng`/`osd`), OpenCV, openpyxl, NumPy.
- **Кэш и фоновые задачи:** Redis 7, Celery 5.
- **Frontend:** HTML, CSS, Vanilla JS SPA, Tailwind CSS (CDN).
- **Тестирование:** pytest, pytest-asyncio, httpx, asgi-lifespan.
- **Контейнеризация:** Docker, Docker Compose, Render (`render.yaml`).

## Быстрый запуск

Нужны только Docker Desktop (или Docker Engine) и Docker Compose v2 — Python, PostgreSQL, Tesseract и остальные зависимости ставятся в контейнерах.

```bash
git clone https://github.com/SHAMBALENOK/Papaya.git
cd Papaya
cp .env.example .env      # необязательно: значения по умолчанию рабочие
docker compose up -d --build
```

После запуска доступны:

- приложение — http://localhost:5000
- интерактивная документация API — http://localhost:5000/docs
- pgAdmin — http://localhost:5050 (логин `postgres@postgres.com`, пароль `postgres`; хост `postgres`, порт `5432`, база `postgres`)

Ключевые переменные окружения (подробности — в `.env.example`):

- `JWT_KEY` — секрет подписи JWT; в production длинная случайная строка (`python -c "import secrets; print(secrets.token_hex(32))"`);
- `ENVIRONMENT` — `development` (по умолчанию) или `production` (включает `Secure`-флаг cookie и запрещает секрет-заглушки);
- `DATABASE_URL` — подключение к PostgreSQL; миграции применяются автоматически при старте;
- `MAX_UPLOAD_MB` — максимальный размер загружаемого документа (по умолчанию `30`);
- `DOCS_DIR` — каталог хранения загруженных документов-источников;
- `RSOSH_EXECUTION` — `auto` (по умолчанию), `celery` или `inline`;
- `RSOSH_PDF_DPI` — разрешение рендеринга страниц PDF для OCR (по умолчанию `300`).

### Образ

Образ собирается из `python:3.11-slim-bookworm` и ставит Tesseract (`rus`, `eng`,
`osd`) и Python-зависимости из `requirements.txt`. Пакеты, установленные
исключительно ради сборки, не выделяются: `pip` не использует `apt`, поэтому
чистить нечего, а `apt-get purge --auto-remove` без списка пакетов удалял бы
часть runtime-окружения вместе со списками apt. `setup.sh` приводится к LF в
образе, поэтому контейнер стартует независимо от настроек git на машине
разработчика (checkout с CRLF иначе даёт `exec /setup.sh: no such file or
directory`).

> В режиме разработки `web`, `celery` и `test` монтируют рабочее дерево (`./app`, `./migrations`, `./scripts`), поэтому правки в коде подхватываются без пересборки образа. Изменение `requirements.txt` требует `docker compose build`.

Логи и остановка:

```bash
docker compose logs -f web celery
docker compose down        # данные в volumes сохраняются
docker compose down -v     # полная очистка: БД и Redis удаляются
```

## Тесты

Тесты идут в изолированном контейнере профиля `testing`: рабочая БД не затрагивается (создаётся отдельная база `papaya_test`, накатываются миграции, Redis очищается). Перед каждым тестом каталоги, документы и пользователи пусты — тесты не зависят от порядка.

```bash
docker compose --profile testing run --rm test
```

Подмножество тестов:

```bash
docker compose --profile testing run --rm --entrypoint sh test -c \
  "pip install --no-cache-dir -q -r /app/requirements-dev.txt && pytest -q tests/test_rsosh_import.py"
```

Что покрыто:

| Файл | Сценарии |
|------|----------|
| `tests/test_auth.py` | регистрация, вход, выход, cookie-флаги, пароли |
| `tests/test_health.py` | liveness, readiness, JSON-404 для не-API путей |
| `tests/test_catalog.py` | публичные каталоги, поиск, дубли, архив, единый поиск |
| `tests/test_bvi.py` | обе стороны связи, заявки, модерация, отсутствие дублей, права |
| `tests/test_roles.py` | границы ролей: школьник / представитель / администратор |

## API

Все маршруты — под префиксом `/api/v1`. Авторизация — JWT в HttpOnly-cookies (`access_jwt`, `refresh_jwt`), защита от CSRF через `SameSite=Lax`, `Secure` в production. Полная схема — http://localhost:5000/docs.

Каталоги и поиск публичные:

| Маршрут | Назначение |
|---------|-----------|
| `GET /api/v1/universities?search=` | каталог университетов |
| `GET /api/v1/universities/{id}` | страница университета |
| `GET /api/v1/universities/{id}/olympiads` | олимпиады с БВИ (`?include_pending=true` — со своими заявками) |
| `GET /api/v1/olympiads?search=&include_archived=` | каталог олимпиад |
| `GET /api/v1/olympiads/{id}` | страница олимпиады |
| `GET /api/v1/olympiads/{id}/universities` | университеты, дающие БВИ за олимпиаду |
| `GET /api/v1/search?q=` | поиск по обоим каталогам |

Управление (роль `ADMIN`): `POST /api/v1/universities/add_university`,
`POST /api/v1/universities/edit_university/{id}`, `POST /api/v1/olympiads/add_olympiad`,
`POST /api/v1/olympiads/edit_olympiad/{id}`, `POST /api/v1/admin/archive_olympiad/{id}`,
`GET/POST /api/v1/admin/*`, `POST /api/v1/docs/upload`, `POST /api/v1/imports/*`.

Связи БВИ: `POST /api/v1/universities/{id}/bvi` (заявка),
`POST /api/v1/universities/{id}/bvi/remove`,
`POST /api/v1/universities/{id}/bvi/{olympiad_id}/moderation` (модерация:
`confirm` / `reject` / `revoke`).

Особенности API:

- неизвестные пути под `/api/v1/` возвращают JSON 404, а не HTML-заглушку SPA;
- health: `GET /api/v1/health` (liveness) и `GET /api/v1/ready` (readiness, проверяет PostgreSQL и Redis);
- ответы об ошибках — единый JSON `{"detail": ...}` без утечки внутренних деталей.
